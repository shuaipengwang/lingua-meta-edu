# 数字人少儿英语陪练 App — MVP 设计文档

> 日期：2026-09-08
> 方案：B（MVP 竖切）— 跑通"数字人老师带读 → 孩子跟读 → 评分 → 反馈"一条核心体验闭环
> 状态：设计已与用户逐节确认，待用户最终审阅
> 修订：2026-09-08 — 前端由 Flutter 原生 App 切换为"公众号 + 关联小程序"，理由是分发零摩擦 + 微信录音 API 稳定

---

## 0. 范围与目标

**目标**：用数字人替代真人外教，做一款少儿英语口语陪练 app，验证"孩子+家长是否买单"这一核心假设。

**MVP 范围红线（明确不做）**：
- 不做自由对话（LLM 接入）— 留给下一版
- 不做家长端详细报告 — 只做最简进度（星星/关卡）
- 不做内容后台 — 课程数据写死
- 不做支付/会员 — 后置
- 不做离线模式 / 端侧 ASR / 账号找回

**默认假设（已采纳）**：
- 目标 4–12 岁，零基础~初级为主
- 课程形态：结构化闯关为主，每节末尾一小段自由对话（自由对话在后续版本）
- 数字人形态：2D 卡通虚拟形象（小程序内用 Rive/Lottie）
- 平台：**公众号 + 关联小程序**（家长扫码即用，零安装；录音走微信原生 API 稳定）
- 数字人/语音能力：首版用第三方，不自研

## 1. 总体架构与技术选型

### 三层架构

```
公众号（渠道） → 关联小程序（前端）  ←→  后端编排服务  ←→  第三方能力（数字人 / 语音套件 / 内容与进度库）
```

后端编排服务是核心枢纽（焦点），负责把课程内容、数字人渲染、语音识别/评测/合成串起来，本身不下场做模型推理。公众号只承担拉新与入口分发，不承载产品逻辑。

### 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 渠道 | 独立公众号 | 已有渠道，菜单/推文挂小程序卡片，分发零摩擦 |
| 前端 | 微信小程序 | 扫码即用、零安装；`wx.getRecorderManager` 原生录音稳定；2D 卡通用 Rive/Lottie 小程序版 |
| 后端 | Node.js + TypeScript | 轻量、生态好，做会话编排和对接多个 AI API 顺手；与小程序云调用契合 |
| 数字人 | 第三方服务 | 候选：火山引擎/腾讯智影/硅基；关键看是否支持 2D 卡通 + 实时口型 + 低延迟音频驱动 |
| 语音 | ASR + TTS + 发音评测打包 | 候选：讯飞（发音评测强、少儿场景成熟）、微软（发音评估 API）；TTS 童声友好、可调语速 |
| 数据 | Postgres + 对象存储 | 课程结构化数据进 PG；音频/数字人素材进对象存储，DB 只放引用 |

### 小程序约束与对策

- **主包 2MB 限制**：数字人形象素材分包加载或放 CDN，主包只放骨架与必需 UI。
- **数字人渲染**：Rive 小程序版或 Lottie 实现简单口型同步；复杂动画性能弱于原生，MVP 用简化 2D 形象验证体验够用。
- **录音**：`wx.getRecorderManager`，输出格式选 mp3/aac 供 ASR 接收；按住说话交互用 touchstart/touchend 控制。
- **审核**：小程序审核 1-3 天，比 App 快；少儿教育类需注意资质与内容规范。
- **后台保活**：陪练本就是"用一会即关"，不需要复杂保活。

### 后端职责

- 调度中枢：把请求路由到合适的第三方能力
- 会话编排：管理一节课内句子流转、评分阈值、反馈分支
- 进度读写：UserProgress / SentenceAttempt 落库
- 对接小程序登录态：`wx.login` → code 换 openid，用 openid 作 user 锚点（替代本地 user_id）

## 2. 核心功能与界面流程

### 主路径

打开 App → 首页 → 选课 → 上课页（核心）→ 课末小结

### 页面功能

**首页**
- 今日推荐课程（基于上次进度）
- 关卡入口（已解锁可点，未解锁灰）
- 学习连续天数（激励留存，MVP 只做数字显示）

**选课**
- 主题关卡列表（如"动物""颜色""问候"）
- 显示解锁状态 + 难度星级
- MVP 只做 3–5 个主题，验证"选→学→得星星"闭环

**上课页（核心）** — app 的灵魂，循环结构
- ① 老师带读：数字人口型同步说一句英文，句子卡同时高亮
- ② 孩子跟读：点麦克风按钮录音
- ③ ASR + 发音评分：识别说了什么 + 给分（音准/流利度）
- ④ 反馈：高分 → 老师鼓励（"Great!"+ 贴纸）；低分 → 老师慢速再读一遍，孩子再试
- 一句过 → 下一句，循环直到本课句子走完

**课末小结**
- 本课得星数（1–3 星，按整体通过率）
- 奖励贴纸（收集感，纯前端）
- 进度条 + "下一关"入口

### 关键交互细节

- **录音：按住说话**（孩子好理解，不是长按复杂手势）
- **反馈即时**：录音结束 → 评分 ≤2 秒返回，否则孩子会走神
- **老师反馈永远正面为主**：即使重试也是 "Let's try again!"，不出现"错误/失败"字样
- **句子卡配图**：每个单词配小图标，帮助零基础孩子建立词义关联

### 激励体系

- 星星（1–3 星/课）+ 贴纸（收集感），纯轻激励
- 不做角色养成等更重的成长体系

## 3. 数据模型与课程结构

### 5 张表 — 内容只读 + 进度可写

**内容层（写死，只读，全局共享）**

- **Theme 主题**：theme_id, name（如"Animals"）, cover_image, order
- **Lesson 关卡**：lesson_id, theme_id, title, difficulty(1-3), unlock_rule
- **Sentence 句子**：sentence_id, lesson_id, en_text, cn_text, audio_ref, image_ref
  - audio_ref：老师标准发音音频（TTS 预生成或现成素材）
  - image_ref：句子配图/单词小图标

**进度层（用户产生，可写）**

- **User**：user_id, openid, nickname, avatar, created_at（openid 由 `wx.login` 换取，作 user 锚点；nickname/avatar 首次进入选头像即设）
- **UserProgress**：user_id, lesson_id, stars(1-3), status(locked/unlocked/done), updated_at
- **SentenceAttempt**：attempt_id, user_id, sentence_id, score, retry(bool), created_at（每次跟读一条记录；retry 标记本次是否为重试，用于错误处理分支）

### 关键设计决策

1. **内容 vs 进度分离**：内容表只读、全局共享；进度表按用户写。后续加内容后台时不用动进度逻辑。
2. **unlock_rule 简化**：MVP 用"前一关得 ≥1 星即解锁"，不做复杂前置条件。字段预留，规则在后端逻辑里判断，不进 DB。
3. **Attempt 必存**：即使孩子重试也记一条。MVP 不为报告，而是为了后续判断"哪句普遍卡住"来调内容，也为后续家长报告铺路。
4. **音频/图片用 ref 不存 blob**：存对象存储 URL，DB 只放引用。节省存储、便于 CDN。
5. **MVP 内容规模**：3 主题 × 4 关卡 × 6 句子 = 72 句，约 8 节完整课。够验证闭环又不至于内容生产成本爆炸。

### 3 个 MVP 主题建议

零基础友好、有图、词短：
- Animals（动物）：cat/dog/bird…
- Colors（颜色）：red/blue…
- Greetings（问候）：hello/thank you…

### 用户体系 MVP 策略

- 无需注册登录流程，进小程序静默 `wx.login` 换 openid 作 user 锚点
- 首次进入选昵称 + 头像即建号
- openid 随微信账号走，换设备登录微信后进度自动延续（相比本地 user_id 丢失风险大幅降低）
- 后续如需家长绑定/会员，再扩 User 字段

## 4. 上课循环的技术时序

### 循环 10 步时序

**预加载阶段（无感延迟）**
1. App 进入句子时向后端要当前句数据（文本+音频引用+图标）
2. 后端把句子的标准音 TTS + 口型数据发给数字人服务
3. 数字人在 App 内开口说英文（音频+口型必须预生成缓存，否则实时调很慢）

**录音阶段**
4. 孩子按住麦克风，App 端录音
5. 松手后上传音频到后端

**评分阶段（核心延迟点）**
6. 后端转发音频给语音套件，做 ASR + 发音评分（音准/流利度）
7. 返回识别文本 + 分数
8. 后端按分数阈值决定反馈分支（高分鼓励/低分重试），结果发回 App

**反馈阶段**
9. 后端驱动数字人表现对应反馈
10. 数字人在 App 内播放鼓励/重试动画+台词

### 延迟控制策略

1. **TTS + 口型预生成**：老师带读音频不是实时合成，而是课程上线时批量预生成、CDN 分发。App 内播放纯本地，零延迟。带读音频上线后固定，不可改（已与用户确认接受）。
2. **ASR 评分是唯一网络往返**：整个循环里只有 ⑤→⑧ 走网络。目标 ≤2 秒。讯飞/微软发音评测 API 实测在 1-1.5s，可行。超 2s 降级——先给"听到啦！"占位，避免孩子以为卡住。
3. **反馈预编排**：数字人的鼓励/重试动画和台词预置几套模板（"Great!"+ 笑脸 / "Let's try again!"+ 慢读），后端只返回一个分支指令，App 本地选对应资源播放。本质是"查表+播"，几乎零延迟。
4. **音频短小**：每句英文 5-10 词，录音 3-5 秒，上传快。不做复杂 VAD（静音检测），靠"按住说话"硬切，省一道延迟。

### 降级与边界

- 网络差/ASR 超时：返回中性鼓励"Good try!"+ 标记本次不计星，不让孩子卡住
- 录音权限拒绝：引导开启权限，否则无法上课（硬依赖）
- 识别为空/噪音：当作低分处理，走重试分支但不显示"错误"

### 明确不做

- 不做实时流式 ASR（够用就行，复杂度不值）
- 不做端侧 ASR（精度不够，发音评测必须云端）
- 不做 LLM 生成反馈话术（预置模板足够，且更可控）

## 5. 错误处理与边界

### 容错原则

少儿场景与成人产品不同——**绝不能让错误打断孩子**。所有失败都要伪装成"老师还在跟你玩"，技术问题绝不外露。

**四原则**：
1. **错误永不外露** — 技术问题一律包装成"老师还在跟你玩"，不出现错误码/叹号/红字
2. **课堂不中断** — 能继续就继续，不能就降级，绝不让 6 岁孩子盯着加载圈发呆
3. **计分宽松** — 异常不计星但不倒扣，保护积极性。MVP 不在乎数据干净度，在乎体验
4. **失败可观测** — 所有异常进埋点上报，后台统计转化率/卡点，但绝不打扰用户

### 五类边界处理

| 故障场景 | 孩子看到 | 后台处理 |
|---|---|---|
| ASR 超时 | "Good try!" + 直接进下一句 | 计 attempt 不计星、不重试；标记 timeout |
| 录音无声音 | "Let's try again!" + 老师慢速重读本句 | attempt(score=0, retry=true)，句子不前进 |
| 录音权限拒绝 | 数字人引导"我们要先开一下小话筒哦" | 小程序内二次引导（scope.userSetting）；仍拒 → "只看不读"降级模式 |
| 数字人加载失败 | 降级到静态老师图 + 音频播放（无口型） | 埋点上报，异步后台预加载下一课资源 |
| openid 授权失败 | 无感，重进小程序静默重试 | 极罕见；微信登录态恢复后自动继续，进度随 openid 不丢 |

### MVP 不做的边界处理

- 不做离线模式（无网提示"网络走开了"，不开课）
- 不做端侧 ASR 兜底（精度不够，宁可降级"只读不计分"）
- openid 即账号锚点，无需额外账号找回机制
